# ca-control-signer on a cloud server (privateAI-design-36 step 1c)

The same image that runs as `ca-control-signer` on the PC (services/signer/Dockerfile) runs on Railway or AWS behind the
platform's HTTPS. The data plane (gateway, Presidio, analyst, console, agent) stays on the PC; only the console API's
`-SignerUrl` changes. Punchline: "Control plane in the cloud; data plane where your data lives."

## What moves, what does not

| | Moves to the cloud | Stays on the PC |
|---|---|---|
| ChainAim's AP2 quote key and receipt key | yes (platform secret variables) | removed from the PC once the cloud signer works (seller folder kept as the backup copy, offline) |
| Pricing (catalog, fees, cost model) | yes (baked into the image from `config/`) | the console keeps its own copy for metering only |
| Mandate key registry (public keys) | yes (`config/ap2-mandate-keys.json` in the image) | the tenants' private mandate keys stay in the agent's env file |
| Files, question, result, unmasking | never | yes |
| Paywall + relayer key | not in this step (Stage 3) | yes |

What the cloud signer receives per job: sizes, model ids, token counts, the job id, hashes, amounts, the NEAR payee and
the invoice id. It refuses any other field by name (packages/signer allowlist). The request key (`SIGNER_REQUEST_KEY`)
and HTTPS protect the calls.

## Before either platform (once, on the PC)

1. The signer split works locally: `.\test-console\desk.ps1 -Planes` is all OK with `ca-control-signer` running.
2. The pricing catalog the signer needs is in the image. If `PRICING_CATALOG` in your price file is
   `config/generated/catalog.local.json` (git-ignored, generated by switch-models.ps1), a build from GitHub will not have it:
   either set the start command's `--pricing-catalog` to a committed catalog (for example `config/catalog.bedrock.json`
   or `config/catalog.json`) whose prices match, or build the image on the PC and push it (AWS path B below).
3. Have three values ready from the seller folder's `signer.env` (desk.json `sellerSecretsDir`): `AP2_SIGNING_KEY`, `RECEIPT_SIGNING_KEY`,
   `SIGNER_REQUEST_KEY`. Open the file in Notepad and copy each value straight into the platform's secret field. Do not
   paste them into a chat, a terminal that logs, a commit or a document.

The start command (both platforms), with your price file's values:

```
node services/signer/src/main.ts --host 0.0.0.0 --pricing-catalog config/catalog.bedrock.json --fee-per-model-call-usd <FEE_PER_MODEL_CALL_USD> --fee-analyst-usd <FEE_ANALYST_USD> --near-gas-fee-usd <NEAR_GAS_FEE_USD> --margin-pct <MARGIN_PCT> --min-price-usd <MIN_PRICE_USD> --cost-model config/cost-model.json --terms-url https://github.com/chainaimdev/chainaim-private-ai/blob/main/LICENSE --mandate-keys config/ap2-mandate-keys.json --mandate-audience chainaim
```

`--port` is left out on purpose: the signer then listens on the platform's `PORT` variable.

## Railway (about 45 minutes)

1. Railway dashboard, New Project, Deploy from GitHub repo, `chainaimdev/chainaim-private-ai`. Expected: a service is
   created and a first build starts (it may fail until step 3; that is fine).
2. Service Settings, Build: Builder `Dockerfile`, Dockerfile path `services/signer/Dockerfile`; root directory empty
   (the repository root is the build context). Expected: the settings save.
3. Service Settings, Deploy: Custom Start Command = the start command above (one line). Expected: saved.
4. Service Variables: add `AP2_SIGNING_KEY`, `RECEIPT_SIGNING_KEY`, `SIGNER_REQUEST_KEY` (values from signer.env, one
   line each, the `\n` sequences kept as they are). Expected: three variables, values hidden.
5. Service Settings, Networking: Generate Domain. Expected: `https://<name>.up.railway.app`.
6. Deploy. Expected: the deploy log shows `[ca-control-signer] listening on 0.0.0.0:<port>  AP2 key 83816e6f...  receipt key d27d1e9f...  mandates on (audience chainaim, tenants t02)`.
7. Browser: `https://<name>.up.railway.app/healthz`. Expected: `{"ok":true,"ap2Kid":"83816e6f...","receiptKeyId":"d27d1e9f...","mandates":true}`.
   And `/.well-known/keys`: public keys only.
8. On the PC, `config\local\desk.json`: `"signer": { "mode": "separate", "url": "https://<name>.up.railway.app" }`,
   then `.\test-console\desk.ps1 -All -AllSkipTests`. Expected: the console API log line
   `signer remote: ChainAim's keys and prices at https://<name>.up.railway.app (ca-control-signer)`.

## AWS (about 60 minutes): App Runner

Path A, from the GitHub source is not available for a Dockerfile in a subfolder with this context, so use path B:
build on the PC, push to ECR, run on App Runner.

1. AWS console, ECR, Create repository `chainaim-control-signer` (private). Expected: a repository URI
   `<account>.dkr.ecr.<region>.amazonaws.com/chainaim-control-signer`.
2. On the PC (AWS CLI signed in), from the repository root:
   ```
   aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
   docker build -f services/signer/Dockerfile -t <account>.dkr.ecr.<region>.amazonaws.com/chainaim-control-signer:v2.0.0 .
   docker push <account>.dkr.ecr.<region>.amazonaws.com/chainaim-control-signer:v2.0.0
   ```
   Expected: the push ends with a digest line. The image holds no key (services/signer/Dockerfile copies none).
3. AWS Secrets Manager: one secret per key (`chainaim/AP2_SIGNING_KEY`, `chainaim/RECEIPT_SIGNING_KEY`,
   `chainaim/SIGNER_REQUEST_KEY`), plaintext value from signer.env. Expected: three secret ARNs.
4. App Runner, Create service, Source: container registry, the image above; Port `8780`; Start command = the start
   command above plus `--port 8780`; Environment variables: reference the three secrets by name (App Runner "Secrets
   Manager" variables). Instance role: allowed to read those three secrets. Expected: the service turns Running.
5. Browser: `https://<id>.<region>.awsapprunner.com/healthz`. Expected: the same JSON as Railway step 7.
6. On the PC, desk.json `signer.url` = that HTTPS URL, then `.\test-console\desk.ps1 -All -AllSkipTests`.

## After either: check and clean up

- `.\test-console\desk.ps1 -Planes`: the local `ca-control-signer` is no longer needed; with a cloud URL the console API
  still holds no ChainAim key. Stop the local one with `.\test-console\down.ps1` only if you want the demo to show the
  cloud signer alone.
- A live tab 03 run: "Quote signed by ChainAim ✓" and "Mandate verified by ChainAim's signer ✓" now come from the cloud
  signer; the receipt verifies with the same pinned keys (the key ids did not change).
- Latency: each paid job adds three to five HTTPS calls to the signer (price, quote, mandate check, receipt, settlement).

## What this does and does not prove

It proves the control plane runs on someone else's server with only sizes and hashes, and that the PC holds none of
ChainAim's keys. It does not make the signer's code provable: on Railway or App Runner the platform operator could in
principle read the keys. The next step is a TEE (NEAR Shade Agents on Phala/Dstack TDX, or AWS Nitro Enclaves), on the
roadmap.

## Same version on both planes (privateAI-design-38)

From v2.1.0 the signer writes the job's signed limits into every estimate-first checkout, and the console runs a job
only from them (`--offer-limits-check on`, the default). Deploy the signer and the console from the same tree: a v2.1.0
console paired with a v2.0.0 signer refuses every estimate-first run (422 "the signed quote carries no limits"), and a
v2.1.0 signer refuses a v2.0.0 console's quote request (400 `$.sizeTolerancePct`). desk.ps1 always builds both from one
tree, so this happens only with a hand-mixed deployment.
