## 2. Requester tracking — recommendation and impact

**What the code records today [READ]:** who *paid* (`lending.ts fee --payer borrower|broker|driller|depositor`) and the request id in the memo `chainaim:<service>:<id>` (`src/fee.ts`). Nothing records who *asked*.

**What the Devnet run shows [READ `data/lending/devnet-run.json`]:** two underwriting fees for request `uw-9b8485ee7e`, both "from broker":
- `D71B1852FF1A74EFE4C5E49333F829B554E2BDFE8CEA294431427628D8B16EFF` (2026-10-26 19:18:59Z)
- `72CC81EBBAFA1038452475147B09AAE79E0226C83761EEA56C5D879C1DFDE5DB` (2026-10-27 04:36:27Z)

`fees` in the state file keeps only the second (it is one value per request id), so the state file alone loses history; the ledger keeps both.

**Recommendation (safest): requester = the account that signed the first `underwrite` fee Payment for that request id, read from the ledger.** Shown as **"requested by (payment)"**, never just "requested by".

Why this is the safest:
- It is **signed evidence**: only the holder of that account's key could send the payment. A field written into the pack would be a self-declaration made on the borrower's PC, which is weaker.
- **Zero lending changes**, zero change to pack hashes or attestations already on the ledger.
- Nothing is guessed when there is no fee: the column then says **"unknown — no fee paid"**.

Impact / limits (to accept):
| Case | What the view shows |
|---|---|
| Fee paid by Harbor for Orion's request (today's data) | requested by (payment): Harbor Credit (broker) |
| Requester ≠ payer (e.g. Harbor asks, Orion pays) | shows the payer; the view cannot know who asked |
| More than one fee for one request (today: 2) | first = requester; every fee listed under *charges*; an **info** note "2 fees for one request" (not judged as an error — the code allows it) |
| No fee yet | requester unknown; no row is invented |

Later, if a declared requester is wanted, the stronger option is a second memo on the fee Payment (`chainaim:req:<role>`), which is still signed — a lending change to request separately.

## 3. Underwriting reports (packs) — where they live, and missing ones

### 3.1 Facts [READ]
- `underwrite.ts --out` default **`<repo>/data/lending/packs`**; file `<requestId>.pack.json` (+ `.actus-request/response`, `.gleif-response` files). `data/` is git-ignored, so packs never reach GitHub.
- The pack is PII-free by design; it is produced **where underwriting runs** (the README says "the borrower's PC"); `lending.ts loan --pack` needs it on the **broker's machine** to re-hash before counter-signing.
- `LoanSet.Data` holds `{"v":1,"h":<sha256(pack)>,"r":APPROVE|REFER|DECLINE,"p":<policy id>,"q":<request id>}` (`packages/xls66/src/attest.ts`).
- On this PC `data/lending/packs/` **does not exist**. The current state file (created 2026-10-26) holds **7 loans, all servicing drills** (`requestId: "drill"`, `packFile: "-"`). No underwritten loan (`loanA…`) is in it; the 2026-10-25 run in the lending README is not in this file **[ASSUME]** it was on another PC or the state file was recreated.

### 3.2 Where they should be stored
`data/lending/packs/` on the machine that runs ledger-watch (the broker / ChainAim side), read-only, set by `--lending-packs <dir>`. Copies of reports made elsewhere are placed there by hand (manual), never fetched or generated by the console.

### 3.3 Verdict rules — nothing invented
| Situation | Verdict shown | Label |
|---|---|---|
| Pack present **and** `sha256(pack)` = `LoanSet.Data.h` | pack verdict | **verified ✓** |
| Pack present, no LoanSet yet | pack verdict | **report only — not on ledger** |
| Pack present, hash ≠ `Data.h` | none | **mismatch** (error alert) — both hashes shown |
| No pack, LoanSet.Data decodes | `Data.r` (+ policy `p`) | **attested on ledger — report not available, hash not re-checked** |
| LoanSet.Data missing / not a ChainAim v1 attestation | none | **no attestation** |
| `requestId: "drill"` | none | **servicing drill — not underwritten** |
| Fee paid, no pack, no LoanSet (today: `uw-9b8485ee7e`) | none | **verdict unknown — no report here, no attested loan** |
| DECLINE | only from a pack (a declined request never reaches the ledger) | — |

ACTUS status (PF/DL/DQ/DF/MA) is computed in ledger-watch from the Loan ledger entry with the same rules as `cockpit.ts actus()` [READ], tested against cases built from that code; no lending file changes.
